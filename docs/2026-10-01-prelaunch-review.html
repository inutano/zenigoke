結論

  • ChIP-seq と ATAC-seq の「マッピング率」はアライメント率ではない。実体は「重複除去後に残ったマップ済みリード数 ÷ トリミング後のリード数」で、未マップと PCR 重複の両方で下がる。サブサンプルで測った真のアライメント率の中央値は ChIP-seq 79.8%、ATAC-seq 94.8% で、表示値（59.7%、65.0%）を全試料で上回る。
  • 実際にアライメント率が低い ChIP-seq の主因は、ゼニゴケ以外の DNA の混入である。細菌様の配列とヒト DNA が、収量の少ない IP ライブラリに偏って入っている。PRJNA690531 の H2Aub と H3K27me3 の14試料はアライメント率 13〜29% で、FAIL と判定した。
  • 参照配列 MpTak_v7.1 に葉緑体とミトコンドリアのゲノムが入っていない。BS-seq では31試料中26試料のマッピング率が約 10〜36 ポイント低く出ている。行き場のないオルガネラ由来リードは核ゲノム上のオルガネラ様領域（NUPT/NUMT）に載り、ATAC-seq と input の偽ピークや、BS-seq の偽の低メチル化領域を作っている。
  • BS-seq には試料固有の問題が3件ある。SRX2613745 と SRX2613731 は SRA 上で R1 と R2 が入れ替わっていて、表示中のメチル化率（全コンテキストで約 0.99）は誤りである。DRX162963 と DRX162964 には細菌 DNA が混入し、SRX2613726 は亜硫酸水素塩変換が不十分である（非変換率 9.2%）。
  • 公開中サイトの「IGV で開く」は動いていない。データ URL の連結漏れ、IGV が解釈しない引数形式、ゲノム未指定の3つが重なっている。UI は検索を入口にしたデータポータルへの再構成を提案し、実データで動くモックアップを作った。

表示されているマッピング率は何を測っているか

ChIP-seq と ATAC-seq の値は、上流パイプライン（chip-atlas-pipeline-v2）の scripts/pipeline-v2.sh が stats.tsv の7列目に書く値で、計算式は次のとおりである（同ファイル 299〜300 行）。

MAPPED   = samtools view -c -F 4 <重複除去後の BAM>
MAP_RATE = MAPPED / fastp 通過リード数 × 100
DUP_RATE = 100 − MAP_RATE

分子が重複除去後の数なので、この値は「解析に使えるリードの割合」に当たる。DUP_RATE は 100 から引いただけの値で、未マップと重複を区別していない。たとえば SRX9800303 はサイト上で「マッピング率 9.6%、重複率 90.4%」と表示されている。ログでは重複除去後のマップ済みリードが 11,480,297、fastp 通過リードが 119,369,300 で、式どおり 9.6% になる。一方、サブサンプルで測った真のアライメント率は 12.9% で、未マップの大半は細菌様 DNA だった。

カタログ DB を作るスクリプトにも別の誤りがある。stats.tsv の4列目は常に 0 の固定値だが、パーサはこれを生リード数と見なしているので、以降の列が一つずつずれて格納されている。DB の reads_filtered には生リード数が、reads_mapped には fastp 通過リード数が入っている。

BS-seq の値は意味が異なる。abismal の統計ファイルの最初の percent_mapped 行で、ペアエンドでは整合ペアの割合、シングルエンドではリードの割合であり、どちらも複数箇所にマップしたリードを含む。複数箇所にマップしたリードは BAM に書かれず、メチル化の計算に使われない。たとえば SRX2613734 は 92.1% と表示されているが、一意にマップしたペアは 73.1% である。ペアエンドをリード単位で数えると表示値より 3.8〜12 ポイント高くなるので、シングルエンドとペアエンドの表示値はそのまま比べられない。

マッピング率が低い原因

指標の問題を除いても、アライメント率そのものが低い試料は残る。両 QC エージェントは全試料の先頭 10万〜25万リードを ENA から取り、本番と同じコンテナでトリミングとマッピングをやり直した。そのうえで、葉緑体、ミトコンドリア、phiX、大腸菌、λ ファージを加えた参照や GRCh38 への再マップ、未マップリードの BLAST で行き先を調べた。下の表は、説明できる試料数の多い順に原因を並べたものである。

推奨する対応

2026-10-06 追記：この章の対応はブランチ prelaunch-fixes に実装した。ただし閾値表の BS-seq「変換の向き」は判定に加えていない（abismal -R で向きの問題そのものがなくなったため）。また SRX29617452 は、推奨した 12 スレッドではなく 16 スレッドで再実行し、完走した。オルガネラを加えた参照での再解析は 157 実験すべてで完了し、出力を差し替えてカタログを作り直した。QC 判定は PASS 70、WARN 72、FAIL 15 になった。PRJNA1289709 の ChIP-seq 7 実験はピークが出ない。オルガネラ由来の積み上がりが消えて MACS3 がシフトモデルを作れなくなったためと考えられるが、ログには「ピークなし」としか残っていない（3実験は旧解析でも 0 件。SRX29617446、449、455 は旧ピークの 46〜59% がオルガネラ様領域にあった）。公開サイトへの反映は所有者の確認待ちである。旧出力との比較は docs/qc/2026-10-06-rerun-summary.md にある。

再解析なしで直せるもの

  1. DB パーサの列ずれを直し、表示名を「使えるリードの割合（重複除去後）」に変える。QC の TSV を sample_qc 表として取り込み、真のアライメント率と判定をサイトに出す。修正案の差分は ChIP/ATAC QC レポートの6章にある。
  2. オルガネラ様領域の BED（1,278 領域、ゲノムの 0.13%）を、ピーク表示と enrichment 解析の除外リストに使う。
  3. Methods ページの「q-value thresholds 0.05, 0.10, 0.20」を「q < 1e-5、1e-10、1e-20」に直す。MACS3 は -q 1e-05 で実行されている。
  4. IGV 送信の URL 連結と引数を直す（5章の Phase 0）。
  5. 抗体名のキュレーションを直す。実験タイトルと矛盾するものが11件ある（例：SRX29617466、480、481 と SRX9800283〜287 は H3）。PRJNA690531 では6実験の抗体欄に遺伝子型名が入っている。

再解析が要るもの

  1. 参照に葉緑体（AP025455.1）とミトコンドリア（AP025456.1）を加え、3アッセイを再実行する。ChIP/ATAC は約49計算時間、FASTQ 約 490 GB の再取得が要る。BS-seq はメチル化の集計前に核ゲノムに絞り、葉緑体の CHH を非変換率の列として残す。
  2. BS-seq の abismal 呼び出しに -R を付ける。
  3. BS-seq パイプラインに CPG_COUNTS[MpTak_v7.1]=20705802 を加える。未定義のため、cpg_coverage が inf または 0 になっている。
  4. SRX29617452 を THREADS=12 で再実行する。
  5. 重複率を正しく出すため、samtools markdup -f の統計から MAP_RATE と DUP_RATE を分けて計算する。上流は変更を受け付けない方針なので、ラッパー側で行う。

ミトコンドリアには、2つの QC エージェントが別々の配列を使った（AP025456.1 と MK202951.1）。NCBI で確認すると、AP025456.1 は葉緑体の AP025455.1 と同じ Tak-1 株由来、MK202951.1 は別株（KBDI00084）由来である。参照に加えるなら AP025456.1 を推奨する。長さの差は1塩基で、QC の結論は変わらない。

5

UI の提案

現行サイトで3つの流れを妨げているもの

  • IGV 連携が壊れている。report/assets/matrix.js の dataUrl() はベース URL 末尾の / を落としてから区切りなしでパスをつなぐので、…amazonaws.comoutput/… という URL になる。url|name 形式の引数は IGV に解釈されず、genome= も付かないので、トラックは IGV 既定の hg38 に載る。それでもボタンは「✔ Sent to IGV」と表示する。
  • ゲノムが S3 にない。置かれているのは chrom.sizes だけで、FASTA、.fai、GFF がない。MarpolBase の配布物は索引のない gzip で CORS もないので、IGV デスクトップからも igv.js からも直接は読めない。
  • 作業記録として読める構成になっている。トップページは軸を選んでから使う2軸マトリクスで、Summary と Methods がデータのページと並んでいる。列名も dev_stage、peaks_q5、elapsed_min のような内部名のままである。
  • 検索が弱い。一覧は部分文字列のフィルタしかなく、条件を組み合わせられない。研究、BioProject、PMID、GSM で探す手段もない。
  • 一括ダウンロードがない。ファイルは1つずつのリンクで、サイズもチェックサムも出ない。S3 にある bigBed と QC ファイルにはリンクがない。
  • QC が見えない。問題のある試料を見分ける判定や注記がサイトにない。
  • スマートフォンで読みにくい。一覧表は 390 px 幅の画面で 893 px にはみ出す。

推奨する設計

  • トップページをデータ検索にする。アッセイ、ChIP の標的、遺伝子型、発生段階、組織、処理、研究、QC のファセットと全文検索を置き、条件は URL に持たせて検索結果を共有できるようにする。
  • ページをまたいで保持されるカートを置き、ブラウザ内で5種類の出力（URL 一覧、再開可能な download.sh、メタデータ TSV、ファイル一覧 TSV、IGV セッション XML）を作る。カートの中身もリンクで共有できる。
  • 実験ページに研究と PMID、QC 判定と理由、ファイル表を出す。既存の samples/{ACC}.html の URL は残す。
  • 作業記録のページ（Methods、処理の記録）は About の下へ、マトリクスと Enrichment は Tools の下へ移す。S3 のキーは変えず、わかりやすいファイル名はスクリプト側で付けられるようにする。

スクリーンショットは、QC 調査の結果をモックアップに取り込んだあとに撮った。モックアップの判定と「Aligned」列は2つの QC の TSV から作っている。

手元の IGV への受け渡し

HTTPS のページから http://localhost:60151 を呼ぶ方式には、ブラウザ側の制約がある。Chrome と Edge は 142 以降、ローカルネットワークへのアクセスに許可ダイアログを出し、これは no-cors の fetch にもかかる。Firefox も 151 から同じ仕組みを順次入れている。Safari はページから localhost への呼び出しを遮断する。通常のリンク（トップレベルの遷移）はどれにもかからず、ChIP-Atlas もこれに頼っている。

IGV 側では、/load は読み込みが終わってから応答し（成功は 204、失敗は 200 と本文の「ERROR…」）、常に Access-Control-Allow-Origin: * を返す。ゲノム JSON の id はその JSON 自身の URL にしておく必要がある。IGV は genome= を読み込み済みゲノムの id と比べるので、一致しないとクリックのたびにゲノムが読み直され、トラックが消える。これを踏まえて、次の手順を採った。

  1. ブラウザのローカルネットワーク許可の状態を確かめる。
  2. /execute?command=version で IGV が起動しているか確かめる。
  3. /load?genome=<json>&file=…&name=…&format=…&locus=…&merge=true を、タイムアウトなしで送る。ピークは narrowPeak ではなく bigBed で送る。
  4. 失敗したら代替手段を示す。リンク遷移での送信、IGV セッション XML のダウンロード、ページ内の igv.js プレビュー、リンクのコピーである。

ゲノムの配布

S3 の references/MpTak_v7.1/ に、FASTA（252 MB）と .fai、遺伝子 GFF3（4.1 MB、索引なしの gzip にして遺伝子 ID の検索を効かせる）、id を自身の URL にした IGV 用ゲノム JSON を置く。元のファイルはすべて /data1/zenigoke/references にあり、保管費は月1セント未満である。02-sync-data.sh の同期対象にも references/ を加える。

それまでのつなぎとして、UCSC GenArk の GCA_039105155.1 が使える。アセンブリ名が同じで、10本の染色体の長さが完全に一致し、chr1〜chr8、chrU、chrV が別名として通る。igv.js で S3 の実トラックが描けることも確かめた。ただし遺伝子トラックは MarpolBase の Mp ID ではなく NCBI の ID になる。
